JWT Tokens Explained: How Modern Authentication Works

JSON Web Tokens are everywhere — but how do they actually work? A clear explanation of JWT structure, signing, and security best practices.

2026-05-17 8 min read Security

What is a JWT?

A JSON Web Token (JWT, pronounced "jot") is a compact, URL-safe way to transmit claims between two parties. JWTs are the backbone of modern stateless authentication — instead of storing sessions on the server, the session data travels with the user in a signed token.

Anatomy of a JWT

A JWT has three parts, separated by dots:

xxxxx.yyyyy.zzzzz
 │     │     └── Signature
 │     └────────── Payload (claims)
 └───────────────── Header

The Three Components

// 1. Header (base64url encoded JSON)
{
  "alg": "HS256",   // Algorithm
  "typ": "JWT"
}

// 2. Payload (base64url encoded JSON)
{
  "sub": "1234567890",   // Subject (user ID)
  "name": "Sarah Chen",
  "role": "admin",
  "iat": 1716000000,     // Issued at
  "exp": 1716086400      // Expiration
}

// 3. Signature
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)

How It Works (Auth Flow)

  1. User logs in with username + password
  2. Server validates credentials, generates a JWT
  3. Server returns the JWT to the client
  4. Client stores the JWT (localStorage or httpOnly cookie)
  5. Client sends JWT in Authorization: Bearer <token> header
  6. Server verifies signature — if valid, request proceeds

Common Algorithms

  • HS256 — HMAC with SHA-256 (symmetric, shared secret)
  • RS256 — RSA with SHA-256 (asymmetric, public/private key)
  • ES256 — ECDSA with SHA-256 (modern, efficient)

Security Best Practices

  • Always validate signatures — never trust a token without verification
  • Set short expiration times — 15–60 minutes for access tokens
  • Use refresh tokens — rotate access tokens without re-login
  • Store secrets securely — environment variables, not in code
  • Prefer httpOnly cookies — not localStorage (XSS vulnerable)
  • Include jti — unique token ID for revocation

Never Do These

  • Don't put sensitive data in the payload (it's just base64-encoded, not encrypted)
  • Don't use none algorithm (JWT algorithm confusion attacks)
  • Don't skip signature verification
  • Don't store JWTs in localStorage if you can avoid it

Validate JWTs in Code

// Node.js with jsonwebtoken
const jwt = require('jsonwebtoken');

const decoded = jwt.verify(token, process.env.JWT_SECRET, {
  algorithms: ['HS256'],      // explicitly specify allowed algorithms
  issuer: 'https://auth.example.com',
  audience: 'https://api.example.com'
});
console.log(decoded.userId, decoded.role);

// Express middleware example
function authMiddleware(req, res, next) {
  const authHeader = req.headers.authorization;
  if (!authHeader?.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'missing_token' });
  }
  const token = authHeader.slice(7);
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET, { algorithms: ['HS256'] });
    next();
  } catch (err) {
    if (err.name === 'TokenExpiredError') {
      return res.status(401).json({ error: 'token_expired' });
    }
    return res.status(401).json({ error: 'invalid_token' });
  }
}

Refresh Token Flow: The Complete Picture

Short-lived access tokens (15–60 min) reduce the window of damage if a token is stolen. Refresh tokens (typically valid for days to weeks) let users stay logged in without re-entering credentials:

// Login flow
1. User authenticates with username + password
2. Server creates: access_token (15 min) + refresh_token (7 days)
3. Returns both to client

// Subsequent requests — use access token
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

// When access token expires (401 response)
4. Client sends refresh_token to /auth/refresh endpoint
5. Server validates refresh_token, issues new access_token
6. Old refresh_token is invalidated (rotation) — prevents replay attacks

// Logout — revoke both tokens server-side
7. Delete refresh_token from database
8. Client clears access_token from memory (not localStorage)

JWT Implementation Mistakes That Get People Hacked

The most common JWT vulnerabilities I've seen in real codebases:

  • Algorithm confusion (alg:none): Attackers change the JWT header to "alg": "none" and strip the signature entirely. Always specify allowed algorithms on the server: jwt.verify(token, secret, { algorithms: ['HS256'] }).
  • Algorithm confusion (RS256 → HS256): If your server supports both RS256 (asymmetric, public key) and HS256 (symmetric, shared secret), an attacker who has the public key can trick the server into using HS256. Use a fixed algorithm, don't let the token choose.
  • Missing expiration validation: Not calling jwt.verify() and just jwt.decode() — the token is unverified and could be expired or forged.
  • Storing tokens in localStorage: Any XSS on your page can read localStorage. Use httpOnly cookies for sensitive applications.
  • No jti claim: Without a unique token ID, you can't revoke a specific token — only all tokens for a user.

When JWT Is the Wrong Choice

JWT shines for stateless APIs and SPAs. But for traditional server-rendered apps (Rails, Django, Express with server-side rendering), session cookies are simpler and safer:

  • Cookies are automatically sent with requests — no client code needed
  • httpOnly + Secure + SameSite cookies are immune to XSS token theft
  • Server-side revocation is immediate — delete the session row, token is dead
  • Built-in CSRF protection with SameSite=Strict (modern browsers)

If you're building a traditional web app, session-based auth with httpOnly cookies is the more secure default. Reach for JWT when you genuinely have multiple services that need to verify the same identity without sharing a session store.
